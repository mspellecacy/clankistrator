# Clankistrator: AI Orchestration Framework

Clankistrator is a high-performance, type-safe Rust framework for multi-agent AI orchestration. It decomposes high-level design documents (Markdown) into actionable project tasks, which are then assigned to and executed by specialized AI agents.

## 1. Vision & Core Objectives
The primary goal is to provide a "Chief Architect" agent that can read a comprehensive project design, understand its technical requirements, and orchestrate a fleet of "Specialized Worker" agents to implement the project from start to finish.

- **Rust-Centric**: Leverage Rust's safety and concurrency.
- **Agentic Workflows**: Support hand-offs, reviews, and iterative refinement.
- **Provider Agnostic**: Seamlessly switch between OpenAI, Anthropic, Gemini, or local models.
- **Persistent State**: Maintain a clear "Project Context" representing the project's current state.

## 2. System Architecture

### 2.1 The Orchestrator (Master Agent)
The `Orchestrator` is the central brain. It uses a "High-Level reasoning" model (e.g., GPT-4o, Claude 3.5 Sonnet) to:
1.  **Parse Markdown**: Extract sections like #Vision, #Features, #Infrastructure, #DataSchema.
2.  **Generate Task Graph**: Convert requirements into a `TaskGraph` (DAG) where tasks have dependencies.
3.  **Assign Workers**: Select the appropriate `WorkerAgent` (Infrastructure, Backend, Frontend) for each task.
4.  **Monitor & Review**: Verify that the output of a task matches the original requirement.

### 2.2 Worker Agents (Specialized Personas)
Each `WorkerAgent` is a specialized persona with a specific `System Prompt` and `Toolbox`.
- **Infrastructure Architect**: Tools for file system, Docker, Terraform.
- **Backend Architect**: Tools for DB schema generation, API design, Rust code writing.
- **Design Architect**: Tools for UI component structure, CSS/Styling logic.
- **QA Reviewer**: Specialized in finding edge cases and verifying logic.

### 2.3 The Project Context (State)
A shared, persistent state (e.g., a JSON file or in-memory struct) containing:
-   `design_doc`: The original source of truth.
-   `task_list`: Current status of all tasks (Pending, InProgress, Completed, Failed).
-   `file_map`: Metadata about files generated by agents.
-   `agent_logs`: History of communications and decisions.

### 2.4 Communication Protocol
Agents communicate via **Structured Messages**. Instead of raw text, the Orchestrator expects workers to return a `TaskResult`:
```json
{
  "task_id": "TASK-001",
  "status": "Completed",
  "summary": "Implemented the backend database schema in src/db.rs",
  "files_created": ["src/db.rs", "migrations/initial.sql"],
  "feedback_to_orchestrator": "I used PostgreSQL as requested in the design doc."
}
```
This ensures the Orchestrator can programmatically update the `ProjectContext`.

## 3. Data Schemas (Proposed Rust Types)

```rust
pub enum TaskStatus {
    Pending,
    InProgress(AgentId),
    Completed { output_summary: String },
    Failed { error: String },
}

pub struct ProjectTask {
    pub id: String,
    pub title: String,
    pub description: String,
    pub dependencies: Vec<String>,
    pub status: TaskStatus,
    pub assigned_role: AgentRole,
}

pub enum AgentRole {
    Orchestrator,
    Infrastructure,
    Backend,
    Frontend,
    QA,
}

pub struct ProjectContext {
    pub project_name: String,
    pub tasks: Vec<ProjectTask>,
    pub working_directory: PathBuf,
}
```

## 4. Tool & Function Interface
Agents interact with the world via `Tools`. Clankistrator uses the `Rig` library's tool abstraction.

### 4.1 Essential Tools:
- `read_file(path: String)`: Returns file content.
- `write_file(path: String, content: String)`: Writes content to disk.
- `list_files(directory: String)`: Lists files in a directory.
- `execute_command(command: String, args: Vec<String>)`: Runs shell commands (sandboxed or restricted).
- `spawn_agent(role: AgentRole, task_id: String)`: (Orchestrator only) Hands off a task to a worker.

## 5. Workflow Execution Loop
1.  **Bootstrap**: User provides `design.md`.
2.  **Analysis Phase**: Orchestrator reads `design.md` and generates the `ProjectContext` with an initial `TaskGraph`.
3.  **Dispatch Phase**: Orchestrator identifies "Ready" tasks (all dependencies met).
4.  **Execution Phase**:
    - For each Ready task:
        - Orchestrator spawns a `WorkerAgent`.
        - Worker receives task details + relevant context.
        - Worker uses `Tools` to implement the task.
        - Worker returns `TaskResult`.
5.  **Review Phase**: QA Agent reviews the `TaskResult`. If it fails, the task is marked `Pending` again with feedback.
6.  **Iteration**: Repeat steps 3-5 until all tasks are `Completed`.

## 8. Security & Safety
- **Sandbox**: All shell commands should ideally run in a containerized environment (e.g., Docker) or a restricted sub-shell.
- **Cost Controls**: Implement token limits and budget tracking for LLM usage.
- **Validation**: Ensure file writes do not exit the designated project root.

## 9. Phase 1 Implementation Summary (AI Agent Reference)
Phase 1 has established the foundational "Skeleton" of Clankistrator.

- **Core Data Structures**: `src/context.rs` contains the `ProjectContext` and `ProjectTask` types, which are serialized using `serde`. These will be the primary state containers for the orchestrator.
- **Markdown Parsing**: `src/parser/markdown.rs` provides `MarkdownParser`, which uses `pulldown-cmark` to extract logical sections based on headers.
- **Environment Management**: The system supports `.env` and `.env.local` files via `dotenvy`, with `.env.local` taking precedence for local development secrets.
- **LLM Connectivity**: `src/main.rs` demonstrates basic LLM interaction using the `rig` library. It can summarize the design document if an `OPENAI_API_KEY` is provided.
- **CLI Interface**: Uses `clap` to handle `--design <PATH>` and `--output <DIR>` arguments.
- **Project Layout**: The module structure is set up for `agents`, `orchestrator`, `parser`, and `tools`, following the target architecture.

## 10. Phase 2 Implementation Summary (AI Agent Reference)
Phase 2 has implemented the core "Brain" of Clankistrator, enabling multi-agent orchestration.

- **Orchestrator Logic**: `src/orchestrator/mod.rs` contains the `Orchestrator` which handles project bootstrapping (decomposing design into tasks) and the execution loop.
- **Worker Abstraction**: `src/agents/mod.rs` defines the `Worker` trait and `GenericWorker` struct, allowing specialized agents to be instantiated for different roles.
- **Task Management**: `ProjectContext` in `src/context.rs` now includes methods for identifying "ready" tasks based on dependency resolution.
- **System Prompts**: `src/orchestrator/prompts.rs` defines the persona for the Chief Architect, providing guidance on task decomposition and review.
- **Agent Spawning**: A `SpawnAgent` tool (`src/tools/spawn_agent.rs`) has been added as a placeholder for the Orchestrator to dynamically delegate work.
- **End-to-End Workflow**: `src/main.rs` now orchestrates a full cycle: loading a design, bootstrapping tasks, and running a task execution iteration.

## 11. Phase 3 Implementation Summary (AI Agent Reference)
Phase 3 has added "The Hands" to Clankistrator, providing agents with the ability to interact with the file system and execute commands, along with a review loop.

- **File System Tools**: `src/tools/file_system.rs` implements `ReadFile`, `WriteFile`, and `ListFiles` using `rig`'s tool abstraction. These allow agents to manipulate the codebase directly.
- **Command Execution**: `src/tools/command_executor.rs` implements `ExecuteCommand`, enabling agents to run shell commands like `cargo check` or `cargo test` to verify their work.
- **Worker Toolbox**: The `GenericWorker` in `src/agents/mod.rs` has been updated to include all file system and command execution tools in its toolbox.
- **Orchestrator Toolbox**: The `Orchestrator` in `src/orchestrator/mod.rs` now includes the `SpawnAgent` tool for dynamic agent delegation.
- **Review Loop**: The `run_iteration` loop in `Orchestrator` has been expanded to include a "Review Phase". Tasks are now moved to `ReadyForReview` after execution and then processed by a specialized QA agent.
- **Enhanced Task States**: `src/context.rs` has been updated with new `TaskStatus` variants: `ReadyForReview` and `Reviewing`, to support the multi-stage execution and review process.
